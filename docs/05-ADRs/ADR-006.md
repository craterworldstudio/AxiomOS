# ADR-0006 — Capability Identity and Handle Representation

## Status

Proposed

## Context

Axiom requires capability lookup to be fast while preventing stale userspace references from regaining authority after a CSpace slot has been reused.

A raw slot index is insufficient because:

```text
generation 1:
    Slot 4 → Endpoint A

delete

generation 2:
    Slot 4 → Endpoint B
```

A stale reference to Slot 4 could otherwise accidentally acquire authority over Endpoint B.

## Decision

A userspace capability handle is an opaque reference containing:

1. A location identifying the capability slot.
2. A temporal identity identifying the current incarnation of that slot.

The exact binary representation is deliberately provisional.

A possible implementation is:

```text
┌──────────────────────┬──────────────────────┐
│      generation      │         slot         │
└──────────────────────┴──────────────────────┘
```

The final bit allocation is not part of this decision.

## Capability Identity Model

Axiom distinguishes four concepts:

```text
Capability
    = authority edge

Object
    = resource being authorized

Slot
    = location containing an authority edge

Generation
    = incarnation of that slot
```

Capability object identity is therefore independent of the userspace handle.

## Copy

Given:

```text
Slot 1 ──► Endpoint E
```

copying the capability into Slot 2 produces:

```text
Slot 1 ──┐
         ├──► Endpoint E
Slot 2 ──┘
```

Slot 2 receives its own slot generation.

The two capabilities refer to the same underlying object but represent separate authority edges.

If the copy is restricted, Slot 2 may possess fewer rights than Slot 1.

## Delete

Deleting Slot 1 removes only that capability edge:

```text
Slot 1 ──X
Slot 2 ─────► Endpoint E
```

The Endpoint remains accessible through Slot 2.

The generation associated with Slot 1 advances so that stale handles referring to the previous slot incarnation cannot regain authority.

## Revoke

Revoking the capability in Slot 1 removes the capability and capabilities derived from it:

```text
Slot 1 ──X
Slot 2 ──X
```

assuming Slot 2 was derived from Slot 1.

The underlying Endpoint remains alive if another independent capability refers to it.

Revocation therefore operates on **capability lineage**, not merely object identity.

## Destroy

Destroying Endpoint E invalidates the object itself:

```text
Slot 1 ──X
Slot 2 ──X
Slot N ──X
```

All capabilities referring to Endpoint E become unusable, regardless of their generation or derivation lineage.

The kernel may reclaim the physical object storage only after all internal references have disappeared.

## Invariants

* A handle MUST NOT contain a kernel memory pointer.
* A stale handle MUST NOT regain authority through slot reuse.
* Slot generations are independent of object identity.
* Multiple capabilities may refer to the same object.
* Multiple capabilities may have different rights to the same object.
* Revocation operates through capability lineage.
* Destruction operates on object identity.
* For the initial flat CSpace, ordinary capability lookup is O(1).
* The exact handle bit layout is provisional until the ABI is stabilized.

## Consequences

### Easier

* Clear separation between authority, object lifetime, and slot identity.
* O(1) initial capability lookup.
* Explicit stale-reference protection.
* Capability copying does not require duplicating the underlying object.

### Harder

* Capability lineage must be tracked for revocation.
* Slot generations must be managed safely.
* Object destruction requires tracking all outstanding kernel references.

## Alternatives Considered

### Raw Slot Index

Rejected because slot reuse creates stale-reference ambiguity.

### Global Object UUID

Rejected as the primary invocation mechanism because resolving a global identifier would require additional lookup machinery and would unnecessarily couple handle identity to object identity.

### Generation Stored Only on the Object

Rejected because multiple independent capability slots can legitimately refer to the same object and must be independently deletable.

## Relationship to Axiom 0

Capability lineage represents edges in the authority graph.

Slot generation represents temporal validity of a particular authority reference.

Object destruction represents invalidation of the authority target itself.

This preserves Axiom 0's distinction between authority delegation, temporal validity, and resource identity.

## Implementation Boundary

### Kernel

* Maintains slot generations.
* Resolves handles.
* Stores capability authority.
* Tracks capability lineage.
* Enforces revocation.
* Tracks object lifetime.

### Userspace

* Treats capability handles as opaque values.
* Does not inspect or construct kernel pointers.
* Does not assume a particular bit allocation before ABI stabilization.

## Future Reconsideration

The handle representation may change before ABI stabilization.

Hierarchical CSpaces, architecture-specific addressing, or hardware capability mechanisms may require a different encoding while preserving the invariants established by this ADR.
