# ADR-011 — Sovereign Capability Filesystem ("VaultFS"), Authority Keyrings, and Interactive Shell Architecture

## Status

Proposed (Target Architecture for Phase 7B)

## Context

Following sovereign screen takeover (Phase 7A), AxiomOS requires a storage and file system architecture to manage configuration files, user data, command scripts, and system utilities.

Traditional Unix/POSIX filesystems present fatal architectural drawbacks for a sovereign capability microkernel:
1. **Ambient Authority**: A single global root directory hierarchy (`/`) accessible to all processes creates confused deputy attacks, path traversal (`../../`), symlink races, and complex ACL permissions.
2. **God-Mode `root` UID**: Unix accounts are flat integers (`UID 0` vs `UID 1000`). If a process obtains `UID 0`, it bypasses all kernel checks, breaking capability security.
3. **Monolithic VFS Bloat**: POSIX VFS specifies hundreds of system calls (`open`, `read`, `write`, `fstat`, `lstat`, `fcntl`, `ioctl`, `mknod`, `chmod`, `chown`...).

AxiomOS requires an original, sovereign filesystem architecture that adheres strictly to object capability principles, eliminates ambient paths, integrates with our Capability Derivation Tree (CDT), and cleanly models user identities.

## Decision

1. **Rejection of POSIX Ambient VFS**:
   - AxiomOS will **not** implement a global ambient root directory (`/`).
   - The microkernel remains completely ignorant of files, directories, paths, and inodes. Storage operations take place strictly via user-mode capability endpoints.

2. **The Sovereign Capability Filesystem ("VaultFS" / "CapFS")**:
   - **Directories as Capabilities**: A directory is an Endpoint capability in a process's CSpace.
   - **Files as Capabilities**: A file is an Endpoint capability derived from a directory.
   - **Operations**:
     - `OP_FS_LOOKUP (name)`: Resolves a relative name within a directory capability, returning a child `CapHandle`.
     - `OP_FS_READ (offset, count)`: Reads a chunk of bytes from a file capability.
     - `OP_FS_WRITE (offset, data)`: Writes a chunk of bytes to a file capability.
     - `OP_FS_CREATE (name, type)`: Carves a new file or directory object.
     - `OP_FS_LIST`: Iterates child directory entries.
     - `OP_FS_STAT`: Returns metadata (size, content hash, modified timestamp).

3. **Per-Process Sovereign Namespaces**:
   - Every process receives its own private root directory capability in its CSpace.
   - When Genesis spawns a child task (e.g. an editor or command), it delegates an attenuated directory capability.
   - If an application is given access to `/home/user/docs`, the rest of the storage tree **physically does not exist** in its address space or CSpace. Path traversal (`../../`) is physically blocked at the capability root.

4. **User Accounts as Authority Keyrings (Not Flat UIDs)**:
   - User identity in AxiomOS is not an integer in `/etc/passwd`.
   - A user account is an **Authority Keyring Capsule**:
     - Holds a private root directory capability.
     - Holds attenuated hardware endpoints (Console, Audio, Network).
     - Holds an identity keypair for signing and proving provenance.
   - Genesis (`root`) holds the unrestricted Root Storage capability.
   - Standard user or guest sessions run in attenuated capsules with no god-mode bypasses.

5. **Two-Stage Storage Implementation**:
   - **Stage 1 (Phase 7B)**: In-Memory RamFS (`libaxiom/fs`) providing high-speed in-memory capability file objects, enabling built-in commands (`help`, `ls`, `cat`, `echo`, `status`, `clear`).
   - **Stage 2 (Phase 7C)**: Block-backed persistent storage server (AHCI / NVMe / FAT32 partition driver) exposed over capability endpoints.

6. **Interactive PS/2 Keyboard Input Integration**:
   - PS/2 Keyboard IRQ 1 is mapped via the microkernel interrupt dispatcher to an Endpoint capability.
   - Genesis or a user-mode input server reads scancodes, decodes them to ASCII keystrokes, and feeds the `root@axiom:~# ` interactive shell line buffer.

## Consequences

- **Positive**: Total elimination of confused deputy vulnerabilities, path traversal exploits, and UID 0 privilege escalation.
- **Positive**: Rights monotonicity is naturally preserved: a read-only directory capability cannot yield a writable file capability.
- **Positive**: Lightweight, transparent, and easy to inspect.
- **Trade-off**: POSIX software cannot be ported directly without a capability adaptation layer (`libaxiom` shim). This is intentional to preserve sovereign security.
