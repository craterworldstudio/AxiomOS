# ADR-012 — Object-Oriented Structural Graph ("CapGraph"), C/ASM Userland Toolchain, and Shell Capability Ledger

## Status

Accepted (Implemented in Phase 7C)

## Context

Following Phase 7B (which introduced basic in-memory RamFS and interactive shell capabilities), AxiomOS faced two major architectural hurdles:
1. **Hierarchical Tree Limitations & Ambient Paths**: Traditional file systems enforce a single global tree or hierarchical paths. Even with capabilities, a tree model forces hierarchical parentage, whereas real-world capability networks form directed graphs with multiple entry points, isolated subgraphs, and mutual delegation.
2. **Monolithic Binary Bloat vs Unix Separation**: Running all shell commands directly inside Genesis (PID 1) creates a bloated root binary and violates the principle of least privilege. In contrast, running standalone binaries typically requires an ELF loader and ambient permissions. AxiomOS requires lightweight, standalone executables in clean C and x86_64 Assembly that execute with strictly attenuated capability keyrings.

## Decision

1. **Object-Oriented Structural Graph ("CapGraph")**:
   - **Directories as Capability Maps**: A directory is an object containing a key-value store where each `Key` is a user-defined string and the `Value` is a capability token `CapToken { target_id, rights }` pointing directly to another object (file blob, another directory map, or a device endpoint).
   - **Graph Topology (No Single Cosmic Root)**: Objects can be linked to multiple directory maps simultaneously, forming a Directed Acyclic Graph (DAG) or cyclic capability network. A process or user only perceives the portion of the graph reachable from their held entry capabilities.
   - **Path Resolution via Iterative Graph Traversal**: Paths like `bin/echo` or `etc/caps.ledger` are resolved by iterative capability dereferences across map nodes.

2. **C and x86_64 Assembly Userland Toolchain**:
   - Built a standalone `userland/` toolchain with custom linker script (`userland/linker.ld`) and crt0 stub (`userland/lib/crt0.s`).
   - Binaries are compiled as raw flat machine code mapped at virtual address `0x500000`.
   - Core utilities migrated from Rust to standalone C and Assembly:
     - `echo.c`: Clean C utility with quote stripping and stdout printing.
     - `whoami.asm`: Pure NASM x86_64 assembly utility querying the active user authority keyring via RIP-relative addressing and Generation-1 handle `0x100000005`.
     - `ls.c`: Clean C utility enumerating entries from `CapMapContext`.
     - `cat.c`: Clean C utility reading file blobs directly from capability pointers in `keyring->storage_cap`.
     - `axe.c`: Fullscreen text and code editor featuring an obsidian status header, line numbering, bottom shortcut cues (`Ctrl+S`, `Ctrl+Q`), and interactive editing.

3. **Shell Capability Ledger (`etc/caps.ledger`) & Principle of Least Privilege**:
   - When Genesis executes a binary from `bin/`, it consults the Capability Ledger (`etc/caps.ledger`).
   - Each binary receives only the exact capabilities mandated by the ledger (e.g. `whoami` receives Console only; `echo` receives Console and storage redirection; `cat` receives Read authority).
   - **Bypass Mechanism (`curr <command>`)**: Users can invoke `curr <command>` to run the executable with the caller's active keyring directly, explicitly bypassing the ledger constraints for debugging or elevated administrative tasks.
   - **Non-Genesis Ledger Updates**: Users can update the ledger via an append-only token protocol enforcing rights monotonicity ($R_{\text{pkg}} \subseteq R_{\text{caller}}$), allowing safe package installation without requiring root keys.

4. **Hardware Syscall Clamping & Memory Hardening**:
   - Extended System V AMD64 ABI clobber definitions in `userland/include/axiom.h` (`"+D"(handle)`, `"+S"(op)`, `"+d"(arg1)`, `"+r"(r10)`, clobbering `"rcx", "r11", "r8", "r9"`) ensuring compiler register allocation survives microkernel zero-out wipes.
   - Expanded Genesis BSS allocation to 64 pages (256 KiB) and mapped 16 physical execution frames (`0x500000`..`0x510000`) for userland program execution.

## Consequences

- **Positive**: Complete architectural decoupling of utilities from Genesis. Every command is an isolated executable.
- **Positive**: Fine-grained capability attenuation at the command level via `/etc/caps.ledger`.
- **Positive**: Elimination of single-root hierarchy; storage is modeled as a true cryptographic capability graph.
- **Positive**: High-performance lightweight C and Assembly utilities with zero runtime overhead.
