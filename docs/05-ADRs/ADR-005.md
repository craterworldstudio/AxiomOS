# ADR-0005 — Capability Fast Path and Revocation

## Status

Accepted

## Context

Axiom 0 defines rich authority semantics including provenance, delegation, membranes, epochs, and revocation.

Evaluating the complete authority history during every IPC operation would make the common invocation path unnecessarily expensive.

Axiom therefore separates ordinary capability use from capability-management operations.

## Decision

The ordinary `INVOKE` fast path must remain bounded and O(1) for the initial flat CSpace design.

The fast path validates the local capability reference and its immediate authority state.

Complex provenance and policy operations occur on explicit slow paths.

## Fast Path

The ordinary invocation path performs approximately:

```text
handle
  ↓
CSpace lookup
  ↓
capability identity validation
  ↓
rights validation
  ↓
object lookup
  ↓
operation dispatch
```

The fast path does not:

* Traverse a provenance tree.
* Reconstruct delegation history.
* Perform cryptographic hashing.
* Consult userspace policy managers.
* Perform unbounded searches.

## Invariants

* Ordinary capability invocation is O(1) for the initial flat CSpace.
* Capability authority is enforced by the kernel.
* Userspace cannot forge a valid kernel capability.
* Revoked authority cannot become valid again through stale references.
* Complex capability-management operations are separate from ordinary invocation.
* Kernel-enforced revocation cannot depend on the continued correctness of a userspace authority manager.

## Revocation Model

Axiom distinguishes three different operations:

### Delete

Removes one capability from one CSpace slot.

The underlying object remains alive if other capabilities or kernel references still exist.

### Revoke

Removes a capability authority edge and all capabilities derived from that edge.

The underlying object remains alive if an independent capability still refers to it.

### Destroy

Invalidates the underlying kernel object itself.

All capabilities referring to that object become unusable regardless of their lineage.

Physical object storage is reclaimed only when no kernel references remain and reclamation is safe.

## Consequences

### Easier

* Fast IPC path.
* Predictable capability lookup.
* Separation of policy from mechanism.
* Rich revocation semantics without imposing provenance traversal on every IPC operation.

### Harder

* Capability lineage must be tracked sufficiently for revocation.
* Slow-path operations may require traversal or indexing structures.
* Object destruction requires careful coordination with outstanding references.

## Alternatives Considered

### Full Provenance Validation on Every Invocation

Rejected because it would place Axiom 0's complete historical model on the IPC hot path.

### Userspace-Only Revocation

Rejected because a compromised userspace authority manager must not be able to resurrect kernel authority after revocation.

## Relationship to Axiom 0

Axiom 0's provenance and delegation model forms the control plane.

The kernel's ordinary capability invocation path forms the data plane.

The control plane determines authority state; the data plane enforces the resulting state efficiently.

## Implementation Boundary

### Kernel

* Capability validity.
* Capability identity.
* Rights.
* Object lifetime.
* Revocation enforcement.
* Object destruction.
* Capability lineage invariants.

### Userspace

* High-level delegation policy.
* Policy decisions about when authority should be revoked.
* Service-level authority management.

## Future Reconsideration

This decision may be revisited if future hardware provides practical mechanisms for inexpensive hardware-enforced capability provenance or equivalent authority validation.
